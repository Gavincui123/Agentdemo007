## 0. 最终部署形态（先看结论）

```
公网 80  ──→ nginx 容器 ──→ 旧 Agent 项目（静态页 + /agent-api/ 反代 8000）
公网 8077 ──→ agentdemo007 容器（本项目，直连发布，闸口在应用内）
内网 docker 网桥 ──→ 应用容器 → host.docker.internal:3379(MySQL) / 6379(Redis) / 5672(MQ) / 8848(Nacos) / 8001(Chroma)
```

| 组件 | 形态 |
|---|---|
| 应用 | 单 jar（含前端 SPA）打成 `agentdemo007` 镜像，仅一个应用容器 |
| 中间件 | **全部复用服务器上已运行实例**（MySQL 3379 / Redis 6379 / RabbitMQ 5672 / Nacos 8848+9848 / Chroma 8001），不新起 |
| 配置 | 连接参数+密钥在 `deploy/.env.prod`（env 优先级最高）；业务结构（LLM providers / RAG 漏斗旋钮）在 Nacos dataId `Agentdemo007-prod.yaml`；闸口在 `agentdemo-gate.json` |
| 编排 | `docker-compose.prod.yml`（仅应用容器），`deploy/nginx-agentdemo007.conf`（备用，当前 nginx 走内联配置） |

关键文件：`Dockerfile`（运行时镜像，零 RUN 层）、`docker-compose.prod.yml`（应用容器 + bash 探活）、`docker-compose.observability.yml`（Jaeger）、`deploy/.env.prod`（密钥，不进仓库）、`deploy/.env.prod.example`（模板）、`.dockerignore`（构建上下文只带 jar）。

## 阶段一：本机打包（mvn clean package 失败 ×3）

### 1.1 写死 `prod` profile → 本机测试全崩（logback 不可写）

- **现象**：`mvn package` 在测试阶段大面积失败，栈里 `Failed to create parent directories for [/var/log/agentdemo007/Agentdemo007.log]` + `Logback configuration error detected`，所有 `@SpringBootTest` 起不来。
- **根因**：`application.yml` 里 `spring.profiles.active` 被写死成 `prod`——打包要跑全量测试，测试上下文以 prod 启动，`application-prod.yml` 的 `logging.file.path: /var/log/agentdemo007` 在 Mac 上不可创建（/var/log 归 root），logback 初始化失败直接炸整个上下文。
- **修复**：改为占位符，本地缺省 dev、容器经 compose 切 prod：
  ```yaml
  spring.profiles.active: ${SPRING_PROFILES_ACTIVE:dev}
  ```
- **教训**：**profile 永远不写死在代码里**。打包（含测试）应该在干净环境跑；验证 prod 的正确姿势是运行时环境变量（见 §1.4）。

### 1.2 写死 Nacos dataId 名

- **现象**：`spring.config.import` 被改成 `optional:nacos:Agentdemo007-prod.yaml`，本地测试也会去拉 prod 配置。
- **根因**：想用 `-prod` 后缀区分 dev/prod 的 dataId，但直接写死了 import URL。
- **修复**：dataId 名参数化：
  ```yaml
  spring.config.import: "optional:nacos:${NACOS_DATA_ID:Agentdemo007.yaml}?group=DEFAULT_GROUP"
  ```
  本地不设 `NACOS_DATA_ID` 读默认；部署时在 `.env.prod` 设 `NACOS_DATA_ID=Agentdemo007-prod.yaml`。**要点：import 里的占位符可以从 OS 环境变量解析**（config data 处理阶段）。

### 1.3 prod 建表配置缺失（潜在雷，当时未爆）

- **现象**：无（表已提前建好掩盖了它）。
- **根因**：`application-prod.yml` 只设了 `spring.sql.init.mode: always`，但 `schema.sql` 位于 `classpath:/sql/` 子目录——Spring 默认只加载 classpath **根**的 `schema.sql`，prod（ddl-auto=none）实际不会执行任何建表。
- **修复**：
  ```yaml
  spring.sql.init:
    mode: always
    schema-locations: classpath:sql/schema.sql
  ```
- **教训**：`CREATE TABLE IF NOT EXISTS` 全幂等，每次启动空跑无害——**这层启动自愈保险值得留着**（后面 §3.4 会因为没留它的权限而踩坑，两者对上了）。

### 1.4 终端没有 JAVA_HOME / 残留环境变量

- **现象**：终端跑 `./mvnw` 直接报 `The JAVA_HOME environment variable is not defined correctly`；或修完 yml 后打包**还是**失败。
- **根因**：①IDEA 里能跑是因为 IDE 自带 JDK 配置，裸终端没有 `JAVA_HOME`；②之前为本地试 prod 在终端/IDE Run Configuration 里 export 过 `SPRING_PROFILES_ACTIVE=prod` / `NACOS_DATA_ID`，残留变量让测试再次以 prod 启动。
- **修复**：
  ```bash
  echo 'export JAVA_HOME=$(/usr/libexec/java_home -v 17)' >> ~/.bash_profile   # zsh 用 ~/.zshrc
  source ~/.bash_profile
  env | grep -Ei 'SPRING|NACOS'    # 排查残留变量，unset 掉
  ```
- **教训**：**同一命令在你机器上失败、在别人（干净）环境成功时，先怀疑环境变量**。本次就是靠「仓库侧连续三次 BUILD SUCCESS」的二分法把问题锁定到终端环境。
- **本地验证 prod 的正确姿势**（单次内联，不污染环境）：
  ```bash
  SPRING_PROFILES_ACTIVE=prod NACOS_DATA_ID=Agentdemo007-prod.yaml \
  LOGGING_FILE_PATH=./data/logs \
  java -jar target/Agentdemo007-0.0.1-SNAPSHOT.jar
  ```
  （`LOGGING_FILE_PATH` 必须带：Mac 上 `/var/log` 不可写。）

## 阶段二：Nacos prod 配置

### 2.1 dataId 命名陷阱：`Agentdemo007-prod.yaml` 不会被读

- **现象**：建了 `-prod` 后缀的 dataId，应用启动日志里**没有** `[Nacos Config] Load config[...] success`，且**没有任何报错**。
- **根因**：dataId 被 `application.yml` 的 import URL 钉死（无环境变量可换名时），`optional:` 前缀让拉不到配置**静默跳过**、不阻塞启动。
- **修复**：两条路——①import URL 参数化（§1.2，最终采用）；②或建独立 prod namespace 且 dataId 同名 `Agentdemo007.yaml`。
- **教训**：**`optional:` 是双刃剑**——可用性好了，但配置读没读到全靠启动日志确认。部署后必查这行：`docker logs agentdemo007 2>&1 | grep "Load config"`。

### 2.2 `NACOS_NAMESPACE=public` 填了显示名

- **现象**：配置拉不到（同样静默）。
- **根因**：namespace 参数必须填**命名空间 ID**（UUID 形态串），不是显示名；public 命名空间的 ID 是**空串**，留空即 public。
- **修复**：`NACOS_NAMESPACE=`（留空）或填真实 ID。

### 2.3 中间件地址写 `127.0.0.1` → Connection refused

- **现象**：启动失败，`entityManagerFactory` → `Failed to obtain JDBC Connection` → `Communications link failure` → `Connection refused`。
- **根因**：**应用跑在容器里，容器内的 `127.0.0.1` 是容器自己**，不是宿主机；MySQL 等中间件在宿主机端口上。RabbitMQ/Redis/Chroma 是懒加载，即使同样错了也可能「成功启动」后运行期悄悄降级——**MySQL 只是第一个炸的，不是唯一错的**。
- **修复**：dataId 里四处地址全改 `host.docker.internal`（compose 已配 `extra_hosts: host.docker.internal:host-gateway`）：
  ```yaml
  spring.datasource.url: jdbc:mysql://host.docker.internal:3379/agentdemo007?...
  spring.rabbitmq.host: host.docker.internal
  spring.data.redis.host: host.docker.internal
  vectorstore.chroma.base-url: http://host.docker.internal:8001
  ```
- **教训**：**容器里的 localhost 语义变了**。容器访问宿主机服务一律 `host.docker.internal`（需 host-gateway）或 docker 网桥网关 IP。

### 2.4 MySQL 授权给错库名 + CREATE 权限缺失（连续两坑）

- **现象 1**：`Access denied for user 'agent_dev'@'%' to database 'agentdemo007'`——网络已通（说明 host.docker.internal 生效），认证通过但无权访问库。
- **根因 1**：授权时建在了别的库名（`agent_demo` ≠ `agentdemo007`）。
- **修复 1**：`GRANT SELECT,INSERT,UPDATE,DELETE ON agentdemo007.* TO 'agent_dev'@'%'; FLUSH PRIVILEGES;`
- **现象 2**：紧接着 `CREATE command denied to user 'agent_dev'@'172.20.0.1' for table 'chat_turn'`。
- **根因 2**：`sql.init.mode: always` 每次启动执行 `CREATE TABLE IF NOT EXISTS`——**MySQL 在发现表已存在之前就先做权限校验**，所以表建好了也必须有 CREATE 权限。
- **修复 2**：`GRANT SELECT,INSERT,UPDATE,DELETE,CREATE ON agentdemo007.* TO 'agent_dev'@'%';`
  （最小权限替代：dataId 里 `spring.sql.init.mode: never`，代价是失去启动自愈建表。）
- **附带认知**：错误里的 `'agent_dev'@'172.20.0.1'` 说明连接经 docker-proxy 转发后源 IP 是网桥网关——MySQL 侧授权用 `'user'@'%'` 即可覆盖。

### 2.5 env 与 dataId 的优先级分工

- **原则**：**OS 环境变量 > Nacos dataId > 本地 yml**。两边都写同名键时 env 赢——dataId 里改了「不生效」八成是被 env 压住了。
- **本次定案**：连接参数/密钥/token 只放 `.env.prod`；业务结构（LLM providers、RAG 漏斗旋钮 `app.rag.*`）只放 dataId（热更新调参面）。**不要把 `RAG_MIN_SCORE` 之类调参键放进 env**，会把 dataId 热更新永久压死。
- **自查命令**：`grep -E "DS_URL|RABBITMQ_HOST|REDIS_HOST|CHROMA_BASE" deploy/.env.prod`——与 dataId 里的值二选一，别双写。

## 阶段三：镜像与容器

### 3.1 服务器拉不到 Docker Hub 镜像

- **现象**：`docker compose up -d --build` 失败：`failed to resolve source metadata for docker.io/library/eclipse-temurin:17-jre ... dial tcp 31.13.87.34:443: connect: connection refused`（DNS 被污染）。
- **修复**：**本地构建镜像整体搬运**，服务器不依赖任何 registry：
  ```bash
  # Mac（Docker Desktop 运行中）
  docker build -t agentdemo007:latest .
  docker save agentdemo007:latest | gzip > /tmp/agentdemo007-image.tar.gz
  scp /tmp/agentdemo007-image.tar.gz root@<服务器>:/opt/agentdemo/
  # 服务器
  docker load < agentdemo007-image.tar.gz
  docker compose -f docker-compose.prod.yml up -d      # 注意：不带 --build
  ```
  `up -d` 不带 `--build` 时本地已有同名镜像就直接用。这也是**日常更新的标准路径**（见 §6）。
- **备选**：配 registry mirror（daemon.json + 重启 docker）——但重启 docker 会把同机的 MySQL/Nacos/Redis 等容器全部带重启，需维护窗口。

### 3.2 宿主 8080 端口已被占用

- **现象**：应用容器绑 `127.0.0.1:8080` 会冲突。
- **根因**：Nacos 容器已发布 `0.0.0.0:8080->8080`。
- **修复**：应用宿主侧换 **8077**（容器内 `server.port` 保持 8080 不动，compose 里 healthcheck 对 `localhost:8080` 是容器内视角，**不要跟着改**）。映射写法 `-p 8077:8080`（宿主:容器）。

### 3.3 端口绑给谁：127.0.0.1 → 网桥网关 → 0.0.0.0（三次演进）

| 版本 | 绑定 | 问题 |
|---|---|---|
| v1 | `127.0.0.1:8080:8080` | ①与 Nacos 的 8080 冲突；②nginx 容器经网关 IP 反代**够不到** 127.0.0.1 绑定 |
| v2 | `172.20.0.1:8077:8080` + `172.19.0.1:8077:8080` | 修复 nginx 可达（nginx 挂在两个自定义网桥，`docker inspect nginx` 查 Gateway）；公网不可达 |
| v3（最终） | `0.0.0.0:8077:8080` | 需求变为「本项目独立 8077 公网入口」：直连发布，**闸口在应用内部（口令+IP 日额），直连依然受保护**，且直连拿到真实客户端 IP、配额更准 |

- **教训**：发布前先想清楚「这个端口给谁访问」——只给 nginx 用就绑网桥网关 IP（公网天然不可达）；要公网直连就 0.0.0.0 + 安全组放行。**网关 IP 用 `docker inspect <容器> --format '{{range .NetworkSettings.Networks}}{{.Gateway}} {{end}}'` 查**，nginx 在自定义网桥时绑 docker0 是够不到的。

## 阶段四：nginx 接入（连续三坑）

### 4.1 conf.d 根本没被 include

- **现象**：`docker exec nginx grep -n "conf.d" /etc/nginx/nginx.conf` **无输出**——主配置没有 `include /etc/nginx/conf.d/*.conf;`，往 conf.d 里 cp 的站点文件**永远不会生效**。
- **根因**：这个 nginx 的真实配置是宿主机挂载的 `/opt/nginx/conf/nginx.conf`（`docker inspect nginx` 的 Mounts 可见），conf.d 里的文件是摆设。
- **教训**：动别人（既有的）nginx 前先查三样：**Mounts（配置挂载在哪）、conf.d 是否被 include、现有 server 块**。

### 4.2 nginx.conf 引用已删除的容器名 → nginx -t 失败 → reload 从未成功

- **现象**：替换配置后浏览器访问 IP 仍是**旧页面**；`nginx -t` 报 `host not found in upstream "ecommerce-service" in /etc/nginx/nginx.conf:34`。
- **根因**：旧配置用容器名 `ecommerce-service` 做 upstream（旧业务后端），容器被下线后 DNS 解析不到 → `-t` 失败 → **reload 从未成功** → nginx 继续用内存里的旧配置发旧页面。
- **修复**：备份后整份替换 `/opt/nginx/conf/nginx.conf`（新 server 块内联，去掉死 upstream），`nginx -t` 通过后 `nginx -s reload`。
- **附带认知**：①`nginx -t` 失败**不影响运行中的实例**（旧配置还在内存里），所以期间没有停机；②「旧前端」不是独立进程，就是旧 nginx 配置发的静态文件——换配置就是换开关。

### 4.3 nginx 里监听 8077 是空转

- **现象**：nginx.conf 加了 `listen 8077` 的 server 块，但 `http://IP:8077` 依然不通。
- **根因**：**nginx 容器的端口映射只有 `0.0.0.0:80->80`**，宿主机 8077 的流量进不了 nginx 容器（端口映射在容器创建时固定，运行中不能加）。
- **修复**：应用直接 `0.0.0.0:8077` 公网发布（§3.3 v3），nginx 只管 80 上的旧项目；nginx.conf 里那个 8077 server 块删除。
- **如果要走 nginx 前置 8077**：必须重建 nginx 容器加 `-p 8077:8077`（同 mounts/同 networks），应用改回绑网桥网关 IP。

### 4.4 误杀风险：heyeAgent 不是旧 Python Agent

- **现象**：`systemctl list-units | grep -i heye` 命中 `heyeAgent-install.service`。
- **澄清**：那是 **百度 HIDS 主机入侵检测探针**，杀了等于拆安全组件。旧 Python Agent 后端要用 `ps -ef | grep python` 另行定位（找 8000 端口进程：`ss -tlnp | grep 8000`），由它的托管方式（systemd/supervisor/nohup）决定下线方法。

## 6. 更新与回滚

```bash
# —— 更新（Mac）——
cd frontend && npm install && npm run build && cd ..    # 前端有改动才需要（SPA 在 jar 里）
./mvnw clean package                                     # 必须 clean：Vite content-hash 累积旧 chunk
docker build -t agentdemo007:latest .
docker tag agentdemo007:latest agentdemo007:$(date +%Y%m%d)   # 日期 tag 便于回滚
docker save agentdemo007:latest | gzip > /tmp/agentdemo007-image.tar.gz
scp /tmp/agentdemo007-image.tar.gz root@<服务器>:/opt/agentdemo/

# —— 更新（服务器）——
docker load < /opt/agentdemo/agentdemo007-image.tar.gz
cd /opt/agentdemo && docker compose -f docker-compose.prod.yml up -d
```

- 配置和数据全在容器外（Nacos / MySQL / Redis / 挂载卷），重建容器不丢。
- 改 Nacos 配置不用重新打包；改后端/前端必须走全流程。
- **回滚**：`docker tag agentdemo007:20260919 agentdemo007:latest && up -d`。
- nginx 配置在宿主机 `/opt/nginx/conf/nginx.conf`（bind mount），改完 `-t` + `reload` 即可，与应用发布无关。

## 8. 模式化教训（下次直接套用）

1. **容器里的 `127.0.0.1` 不是宿主机**——容器访问宿主服务用 `host.docker.internal`（配 host-gateway）或网桥网关 IP。
2. **`optional:` 和懒加载都会把错误变成「静默降级」**——部署后必查启动日志的关键行（Load config / profile / Started），不能只看「进程没死」。
3. **env > Nacos dataId > 本地 yml**——连接参数与调参面分开放，绝不双写同名键。
4. **profile 与 dataId 名不写死**，全部走环境变量占位符；打包永远在干净环境，验证 prod 用运行时内联变量。
5. **同一命令「我失败、别处成功」→ 先查环境变量**（JAVA_HOME / SPRING_* / NACOS_*），用干净环境二分定位。
6. **接手既有 nginx**：先查 Mounts + include 关系 + 现有 server 块，再决定改哪；改完必 `nginx -t`，失败时 reload 不会发生（页面不变≠没生效，= 没加载成功）。
7. **服务器连不上 Docker Hub** 就本地 build + save/scp/load，顺带获得精确回滚能力（日期 tag）。
8. **端口规划先查占用**（`ss -tlnp` / `docker ps`），并明确「给谁访问」决定绑定地址（网桥 IP = 内部，0.0.0.0 = 公网+安全组放行）。
9. **数据库账号**：GRANT 的库名与 JDBC URL 严格一致；`sql.init.mode=always` 需要 CREATE 权限（IF NOT EXISTS 也先查权限）。
10. **杀进程前先认亲**：heyeAgent=百度 HIDS，不是你的业务进程；`ps -ef` + `ss -tlnp` 双重确认。
11. **基础镜像浮动 tag 会被上游换底座**（`eclipse-temurin:17-jre` 漂到 resolute）→ RUN apt 层
    缓存失效后重跑，CN 网络拉不动（archive.ubuntu.com 超时 404；换 aliyun 源 universe 索引
    也连接失败）。最终解法不是换源、也不是翻墙预装，而是**消灭 RUN 层**：Dockerfile 只
    `FROM` + `COPY` jar，构建期零外网依赖；镜像内无 curl/wget，compose healthcheck 改用
    bash 内建 `/dev/tcp` 发 HTTP 探测（dash 没有 /dev/tcp，须显式 bash）。基础镜像钉
    `-jammy`（LTS），即使 tag 再漂移也只是换 COPY 底座。

## 9. 上线手册：Jaeger 链路可视化（Phase 23，2026-10-08 增补）

应用侧已内置 OpenTelemetry（`spring-boot-starter-opentelemetry`，Boot 4 原生 SDK 路线，无 javaagent）：
15 步流水线（root + per-step）、LLM 网关（`gen_ai.*` 语义 span）、RAG 漏斗（retrieve/rerank/gate 分段）、
HTTP 出站（Chroma/embedding/rerank 拦截器）、MQ 消费均已埋点。导出由两个环境变量驱动
（见 `deploy/.env.prod.example`）：

- `OTLP_ENABLED=true` —— 同时打开 OTLP 导出与应用侧 OTel 装配（traceId 对齐、W3C 传播）
- `OTLP_EXPORTER_ENDPOINT=http://jaeger:4318/v1/traces` —— 指向 Jaeger。**两个 compose 文件
  同目录 = 同一 compose 项目 = 同一张 docker 网络，应用直连服务名 `jaeger`，不经宿主端口、
  不碰防火墙**（2026-10-08 生产实证：走 `host.docker.internal` 会被宿主防火墙 reload 丢包，
  见 §9.6 第 8 条；跨项目部署才退回 `http://host.docker.internal:4318/v1/traces`）。
  **必须带 `/v1/traces` 信号路径**：Boot 4 把 endpoint 当完整 URL 直接 setEndpoint，不自动追加，
  少了路径会一直 404 且 Jaeger 侧零数据

> **读法**：§9.1 只在首次安装时做一遍；之后的日常发版只走 §9.2（和普通发版完全一样，
> Jaeger 不动）；出问题先查 §9.6 踩坑速查。

### 9.3 Jaeger 使用指南（怎么看、怎么用）

**搜 trace（三条路，由慢到快）**：① Service 下拉选 `Agentdemo007` → Find Traces（默认最近 15 分钟，
时间窗可调）；② Tags 按属性过滤——`agent.scene=回答生成`（只看终答出站）/ `step.outcome=DEGRADE`
（只看降级过的请求）；③ **把 `X-Trace-Id` 响应头的 32 位 hex 直接贴进搜索框**（traceId 对齐恒开，
这条路永远可用）。

**读瀑布图（五句口诀）**：**左树看层级**（`agent.pipeline` 包 15 个 `agent.step`，步内再包
`gen_ai.chat`/`agent.rag.*`，缩进即父子）；**条宽看耗时**（瓶颈一眼可见）；**点开 span 看 Tags**
（scene/model/attempt/outcome/token 用量，同轮多次 LLM 出站靠 `agent.scene` 分辨）；**顶栏看总览**
（总墙钟、span 数，span 名红 = ERROR 状态）；**异步尾巴同 trace**（MQ 落库晚 ~2s 出现在时间轴最右，
traceId 相同仍在同一张图里）。

**span 字典**：`POST /chat`（server，自动装配）｜ `agent.pipeline`（root）｜ `agent.step`×15
（step.name/outcome）｜ `gen_ai.chat`（LLM 出站，attempt 辨重试）｜ `agent.rag.retrieve/rerank/gate`
（漏斗三段）｜ `HTTP POST`（Chroma/embedding/rerank 出站）｜ `agent.mq.*.process`（异步落库）。
一轮同步 /chat + RAG 命中 ≈24 span，场景不同浮动正常——看结构对不对，不看凑数。

**常见困惑**：搜不到 trace → 按序查踩坑速查第 1 条；一轮对话多条 trace = 多次独立请求（语义如此，
非断链）；流式 span 无父孤立 = 断链 bug（已修，21 span 同链路）。图文详解见系列第十三章
《链路可视化：OpenTelemetry 埋点与 Jaeger》。

### 9.5 端口与安全口径（红线，全程不变）

- **4317/4318 供导出，但应用不走宿主端口**：两个 compose 同目录 = 同一 compose 项目 = 同一张
  docker 网络，应用直连服务名 `jaeger:4318`（见 §9 开头与 §9.6 第 8 条）；宿主映射留给本机直跑/
  跨项目备选。公网不可达靠安全组（只放 80/443/8077），**不新增任何放行端口**。
- **UI 16686 只绑 127.0.0.1**：公网永不直达，只走 SSH 隧道（命令见 §9.2）——Jaeger UI 无鉴权，
  对公网暴露 = trace 内容（含 prompt/对话）裸奔。
- 两个 compose 文件分离（`docker-compose.prod.yml` 应用 / `docker-compose.observability.yml`
  只含 Jaeger）：发版节奏不同（应用每次、Jaeger 一次）、摘除互不牵连、Jaeger down 不影响业务。

### 9.6 踩坑速查（出问题先对号入座）

1. **Jaeger 里查不到 trace**：① 等 8 秒再刷（BatchSpanProcessor 5s 攒批）；② `grep -c
   "Failed to export spans"`>0 → endpoint 缺 `/v1/traces`；③ 采样——默认只有 10%
   （`management.tracing.sampling.probability`），项目已显式设 1.0，勿改回默认。
2. **Boot 4 的 OTLP 属性前缀分裂**：开关在 `management.tracing.export.otlp.enabled`，
   endpoint/transport 在 `management.opentelemetry.tracing.export.otlp.*`——写错前缀
   exporter **静默不装配**（无报错、零数据），这是实测踩过最阴的一坑。
3. **Boot 4 把 endpoint 当完整 URL**：不自动追加信号路径（javap 坐实
   `OtlpHttpSpanExporterBuilder.setEndpoint(属性值)`）。
4. **Boot 4（Framework 7）已移除 `RestTemplateBuilder`**——手建 RestTemplate 的出站 span
   用自写 `TraceClientInterceptor`（observability/trace/）收口，不是换 builder。
5. **OTel SDK 1.4x+ 把 `W3CTraceContextPropagator` 迁进 api**
   （`io.opentelemetry.api.trace.propagation`）——老教程 import 会编译失败。
6. **Jaeger all-in-one 是内存存储**：容器重启丢历史 trace（demo 定位可接受，384m 限定的代价）；
   要持久化再谈（S3/Cassandra/ES，别在这台 4G 机器上想）。
7. **traceId 三处同源是应用契约**：`X-Trace-Id` 响应头 = `UnifiedResponse.traceId` = Jaeger
   Trace ID（`MdcBackedIdGenerator` 恒开实现，不挂 OTLP 开关）——对不上就是坏了。
8. **导出报 `InterruptedIOException: timeout`，容器内 TCP 连 `host.docker.internal:4318` 挂起
   （不拒绝、不超时返回，要 ^C）**：宿主防火墙 reload（`firewall-cmd --reload` / `ufw enable`）
   会丢掉容器→宿主发布端口的转发包，且同路的 MySQL/Redis 活着（极具迷惑性，2026-10-08 实证）。
   解法：endpoint 改服务名直连 `http://jaeger:4318/v1/traces`（同 compose 项目网络，绕开宿主
   防火墙整层变量）；宿主侧自证 Jaeger 活着用 `curl -X POST localhost:4318/v1/traces` → 415。
